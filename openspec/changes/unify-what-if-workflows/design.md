## Context

`App.tsx` currently probes `/api/v2/portfolios` and replaces the entire main application with `EventApplication` for invited users. The main application keeps portfolios in owner-scoped SQLite, renders the desired Overview, Risk, Research, navigation, and onboarding, and compares allocations through the v1 What-if API. The event application keeps separate portfolios and analyses in MongoDB, then uses an analysis ID to create drafts and runs. This split makes existing main portfolios disappear when the event lab becomes available.

Both APIs also persist standalone analyses. V1 saves dashboard metrics in SQLite; v2 saves metrics plus aligned adjusted-price history in MongoDB. Main pages and AI explanations consume those IDs. Event runs already copy much of the analysis input, but draft creation and workers still dereference the separate analysis record. The user wants the main pages preserved, both What-if approaches combined, and standalone saved analyses removed from both workflows.

## Goals / Non-Goals

**Goals:** Keep the main pages and portfolio experience; make one selected, owner-scoped portfolio available to both What-if approaches; retain a fast allocation path and an optional researched event path; calculate current dashboard values automatically without standalone analysis records; preserve exact inputs for durable event results; remove manual analysis controls, raw IDs, and duplicate onboarding.

**Non-Goals:** Change the visual design of Overview, Risk, or Research; add brokerage connectivity, trades, event-occurrence probabilities, or ungrounded AI math; bypass event allowlists, provider rights, or probability calibration gates; migrate the whole application to a new database in this change.

## Decisions

1. **Keep the main application shell and current portfolio store as authority.** `Application` owns routing, navigation, onboarding, and the selected portfolio. Remove the `/api/v2/portfolios` probe as a whole-app mode switch. Use the current owner-scoped v1 portfolio store for both paths; MongoDB stores event drafts, runs, messages, and their immutable context, not another editable portfolio. Event routes resolve the selected portfolio through the same verified owner identity and portfolio repository before accepting new work. Existing Mongo-only portfolios are imported idempotently into the main store with their owner and ID preserved when possible; conflicting records require explicit resolution rather than overwrite. This favors continuity of existing portfolios and availability of basic dashboard pages when the event service is down. Promoting MongoDB as the sole portfolio store would require a broader migration and couple every page to event infrastructure.

2. **Compose one What-if page around one proposed allocation.** Keep the current allocation editor, presets, add/remove ticker behavior, result chart, and explicit “Use this allocation” action. Add an optional “Explore an event” path within the page rather than another global route or app shell. It receives the same current/proposed weights. Quick comparison never invokes Tavily, DeepSeek, or Gemini. Event research begins only after the user chooses a template/situation and starts a draft; it presents sourced facts, missing evidence, proposed shocks with units, a review/confirmation step, and current-versus-proposed one- and three-month cases. A saved event draft is pinned to its original allocation; later editor changes show a stale-state message and require a new draft. Preserve the current combined eight-symbol limit for the first unified release. To support a newly added proposed symbol, the event calculation aligns history for the current/proposed union plus factor proxies and represents absent positions as zero weights. Unsupported or incomplete coverage fails explicitly. Restrict issuer templates to an eligible stock in that union.

3. **Replace standalone analysis persistence with on-demand calculation contracts.** On portfolio selection, reload, and successful edit, the backend calculates current metrics from the configured provider and returns values, observation period, and provenance directly; the React app holds that response in memory across page navigation. There is no manual refresh control and no new SQLite or MongoDB analysis record or public analysis ID. Portfolio and market-data revisions invalidate in-memory results; provider failures surface an unavailable state without substituting fictional values for live data. Allocation comparison calculates both sides over one aligned price window. Overview/Risk/What-if AI requests calculate or validate the exact context used for the answer and return the corresponding metrics with the text, so the UI cannot display an explanation of different numbers. Provider-level rights-compliant price caching is allowed; it is not an application-level saved analysis.

4. **Pin event inputs at draft creation, not in a prior analysis.** After verifying ownership and proposed weights, the event API obtains one aligned adjusted-price window for the current/proposed symbol union and factor proxies, validates coverage, calculates the baseline, and atomically stores portfolio name and revision, allocations, prices, dates, provenance, and model version in the durable draft. Research workers use that context. Confirmation copies or immutably references the draft context in the run together with confirmed shocks, evidence, and results; it never fetches newer prices to rewrite an older draft. Reading saved runs requires the verified owner and retains the original numbers even after portfolio or market changes. This preserves reproducibility without a separately saved analysis entity. Eliminating all persisted inputs would make saved event results unverifiable.

5. **Keep access and disclosure boundaries.** Standard pages remain usable when event dependencies are unavailable. The event path shows a precise unavailable or not-invited state without replacing the dashboard. Tavily retrieval stays on approved hosts, extracted evidence and missing statuses stay visible, Gemini/DeepSeek cannot supply portfolio math, and conditional probabilities remain withheld without accepted calibration. Keep sample/model labels and visible data provenance, but not implementation labels such as “Backend analysis” or opaque IDs.

## Risks / Trade-offs

- [On-demand requests increase Alpaca traffic and latency] → Reuse a bounded, rights-compliant provider price cache and deduplicate concurrent calculations; measure quota and response times before cutover.
- [AI text could refer to metrics from a different market window] → Return the calculation used for each answer and update the displayed metrics atomically, or reject a stale portfolio revision.
- [Current SQLite portfolio storage may not support multi-instance deployment] → Keep it behind a repository interface and treat a shared-store migration as a separate release prerequisite; do not silently mirror editable portfolios in two stores.
- [Old drafts and runs reference analysis IDs] → Backfill their allocation/price/provenance context before deleting analyses. Drain or explicitly cancel in-flight legacy drafts; retain completed results and owner isolation.
- [New proposed symbols may lack aligned history or event-model coverage] → Validate the full union before queuing research and report the missing symbol/date rather than partial modeled output.
- [Removing the analysis-ID API breaks existing clients] → Introduce replacement response contracts, migrate the frontend and workers, then retire the old endpoints after contract tests and reference audits.

## Migration Plan

1. Add the shared owner-scoped portfolio access boundary and inventory any Mongo-only portfolios and legacy analysis references. Backfill v2-only portfolios to the main store without overwriting an owner's existing portfolio; verify counts and ownership.
2. Add on-demand current-metrics and comparison contracts and adapt AI workflows. Keep legacy analysis reads during migration; stop creating new analysis records only after all consumers use the new contracts.
3. Embed complete immutable context in new event drafts/runs, migrate legacy records, and verify stored results before removing the v2 analyses collection and v1 analyses table. Preserve recoverable backups according to the project retention policy.
4. Replace the whole-app mode switch with the main shell and integrated What-if UI. Hide event controls behind the existing internal/public gates until the new path passes owner-isolation, coverage, loading/error, keyboard, and mobile checks.
5. Retire legacy analysis endpoints and duplicate event portfolio UI after usage and reference checks. Roll back the UI/API cutover independently while the legacy reads and data backups remain available; do not roll back by changing historical run inputs.

## Open Questions

- Confirm the deployment target for the authoritative portfolio repository before multi-instance public release; this proposal keeps the existing main store for the first cutover.
- Set a retention period for migrated legacy analyses/backups after every draft and run has been verified independent of them.
